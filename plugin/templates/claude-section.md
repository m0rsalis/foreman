## Working with parallel agents (ops kit)

A **lead** session plans, delegates to background agents, merges and talks to {{OWNER}}. Agents build. These rules are {{OWNER}}'s; follow them without being told again. The kit's skills carry the step-by-step routines: `/ops-kit:restore`, `/ops-kit:checkpoint`, `/ops-kit:check-in`, `/ops-kit:brief`, `/ops-kit:start-agent`, `/ops-kit:revive`, `/ops-kit:merge`. Settings: `.claude/ops-kit.json` (owner, agent cap, locks, full check, panel); `/ops` opens the Ops panel.

- **The lead's session name is `{{LEAD}}`.** Agents report to it by that name. If the lead runs under another name, update `lead` in `.claude/ops-kit.json` and the heartbeat.
- **Agents run as background sessions**, so a clear of the lead never touches them. Start one from the main checkout: `claude --bg -w <task> --agent {{SLUG}}-engineer|{{SLUG}}-implementer|{{SLUG}}-checker --permission-mode auto --name <task> "<prompt>"` (`-w` gives it its own worktree, `.claude/worktrees/<task>`). The prompt points at the brief file and says: `tmp/` paths mean the main checkout's `tmp/`; report to `{{LEAD}}` by name with SendMessage only (one line per merge, then the final report; a hand-back line before stopping on a usage limit); if the lead is unreachable, send the report to `{{HEARTBEAT}}` and carry on; run long commands in the background; no sub-agents. The lead files each report as `tmp/ops/reports/<task>.md` (an agent's sandbox cannot write the main checkout's files). `/ops-kit:start-agent` has the exact command.
- **The agent cap** is `agentLimit` in `tmp/ops/status.json` (default `agentCap` in `.claude/ops-kit.json`). {{OWNER}} sets it and changes it with the usage limits; more agents than the machine can carry slow every agent. When {{OWNER}} makes something "priority one", pause the others (commit work in progress, release locks, end the turn) until it is delivered, then resume them.
- **Pick the model by difficulty:** `{{SLUG}}-engineer` (Opus) for hard logic, architecture, complex merges, design documents and anything where fidelity is the point; `{{SLUG}}-implementer` (Sonnet) for well-specified changes, UI from a clear brief, doc updates, pipelines with clear rules; `{{SLUG}}-checker` (Haiku) for rerunning a full check and merging when green, watching queues, collecting results. The definitions live in `.claude/agents/` and are this project's to edit.
- **Split by track, one agent per track,** one branch and one PR per milestone or fix batch. Large features start with a design note and plan (OPEN questions with proposed defaults); looks {{OWNER}} must approve start with mockups, not finished work.
- **The backlog** is `tmp/ops/backlog.json`. {{OWNER}} describes a feature; the lead and {{OWNER}} define it together; the lead writes it in (status `defined`; a brief file and status `ready` once it can start). When a slot opens the lead takes the best ready item: {{OWNER}}'s `priority` (1 = next) beats the lead's `rank`, every `dependsOn` item is done, it is not blocked; prefer what relates to the current code and the running agents. When unsure, ask {{OWNER}} with a recommendation. The lead keeps backlog.json current at every checkpoint.
- **Briefs are self-contained** (`/ops-kit:brief`): {{OWNER}}'s words, files to read first, the state inherited, what to build, tests, branch names, report format. The agent definitions already carry the machine rules.
- **Shared resources go through the queue:** `{{TOOLS}}/queue.sh <lock> <command...>` (FIFO across every session and worktree, locks in the main checkout's `tmp/agent-locks`; declared locks: {{LOCKS}}). One lock at a time. `{{TOOLS}}/fullcheck.sh` runs the full check ({{CHECK}}) through the queue before every merge; read its final `FULLCHECK:` line.
- **Merge discipline:** when two PRs are close, announce an order. A PR merges main and runs its full check only after the one ahead of it is on main; two checks racing for the same main starve each other.
- **Processes:** agents kill only processes they started, by pid; never pattern kills (`pkill`, `killall`). Never stop a queued job mid-run; the queue clears dead owners by itself.
- **After a merge, remove the agent's worktree:** `claude stop <id>`, then `claude rm <id>`. It refuses while the worktree has untracked files: check they are saved or not needed, delete them, `claude rm` again. Then `git worktree prune`, `git branch -d` for the merged branch (and the `worktree-<task>` branch `-w` made), `git fetch --prune`. Worktrees can hold gigabytes of caches each.
- **Background sessions can die silently** (blocked, no pid) or end on a usage limit (state `done`). Revive with the FULL session id and a message naming its worktree: `claude --bg --resume <sessionId> "<message>"` (`/ops-kit:revive`). `--resume` on a session that is still running starts a copy: check `claude agents --json --all` first.
- **The check-in:** `{{HEARTBEAT}}`, a Haiku background session, messages the lead "check-in (heartbeat)" at :17 and :47 (the lead's own cron jobs die with a clear). On it, run `/ops-kit:check-in`: revive dead agents, fill free slots from the backlog, merge housekeeping. Its cron expires after 7 days: restart it weekly (`{{TOOLS}}/heartbeat.md`).
- **Previews for {{OWNER}}** (images, recordings, reports to look at) go in the main checkout's `tmp/` (the panel lists the configured preview folders), never only in an agent's worktree.
- **Code comments:** agents start every session without memory and read the files they change, not the design notes, so a comment beside the code is where a rule reaches the agent that could break it. Say why, the limits or invariants, the units, and the decision or doc section the code implements. Never restate the name or the code. No history (who asked, when, what it used to be): that lives in git and the docs. Update or delete a comment in the same change as its code; a stale comment misleads an agent more than a missing one.
- **Ask {{OWNER}} one theme at a time,** with a recommendation. Record decisions in the docs in small PRs.

### Lead checkpoints

The lead's conversation is not the record; files are. **The lead never clears itself**: a cleared desktop session has no process until {{OWNER}} writes, so agents and the heartbeat cannot reach it. {{OWNER}} clears by hand.

- **The record** (all of `tmp/` is gitignored and machine-local): `tmp/ops/status.json` (running agents with kind, model, worktree, branch, step, session id; sign-off items for {{OWNER}}; the cap and today's priority line), `tmp/ops/backlog.json`, `tmp/ops/lead-notes.md` (where things are, {{OWNER}}'s directions not yet built, open questions, non-obvious know-how; overwritten at each checkpoint, about a page), `tmp/ops/briefs/<task>.md`, `tmp/ops/reports/<task>.md`.
- **Checkpoint** (`/ops-kit:checkpoint`) whenever an agent starts, hands back or merges, and before every clear.
- **Restore** (`/ops-kit:restore`) at the start of a lead session or after a clear: read the lead notes, run `python3 {{TOOLS}}/lead_status.py`, act on new reports, revive dead agents, carry on.
